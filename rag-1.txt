# ✅ 结论：**可以混合使用，也是企业里非常常见的架构方案**

> 
> SpringBoot 主业务系统（你的Java后端）<--HTTP调用--> RAGFlow API
> RAGFlow 负责：文档上传、解析、OCR、分片、向量入库、混合检索、Rerank、知识库管理
> SpringBoot 负责：业务鉴权、业务逻辑、权限控制、前端交互、业务数据库、组装请求、拿到RAGFlow返回结果后做二次业务处理
> LangChain4j 在这个架构里**可选**：可以不用；也可以只用来做上层Agent编排，底层检索交给RAGFlow。

## 架构简图

```
前端 ↔ SpringBoot业务服务（主系统）
        ↓ HTTP/OpenAI兼容API
      RAGFlow服务（独立部署，Docker）
        ↓
    文档解析 + 向量库 + 检索 + LLM
```

### 两种混合模式可选

#### 方案A：SpringBoot 直接调用 RAGFlow（推荐，最简单）

SpringBoot 只作为**API调用方**，不碰文档解析、向量库、分片这些脏活。
RAGFlow 对外提供两套API：

1. **知识库管理API**：上传文档、删除文档、创建数据集、查看文档状态（后台管理类接口）
2. **对话/问答API（OpenAI兼容格式）**：提问，RAGFlow内部自动做RAG检索+生成回答，并返回引用片段来源。

> 
> 👉 优点：业务代码极少，RAG能力全部托管给RAGFlow；后续优化分片、重排、文档解析，**不需要改SpringBoot代码**，只需要在RAGFlow页面调参。
> 👉 缺点：检索链路在RAGFlow内部，如果你需要**深度介入检索过程**（自定义召回规则、业务过滤条件）灵活性弱一点。

#### 方案B：SpringBoot + LangChain4j + RAGFlow（重度混合）

- RAGFlow：仍然负责文档解析、文档入库、向量存储（当做一个向量检索服务）
- LangChain4j：在SpringBoot内部，做**上层Agent逻辑、Prompt组装、工具调用、结果校验、多轮记忆管理**
- 流程：用户提问 → LangChain4j 做问题改写 → 调用RAGFlow的检索API拿到相关片段 → LangChain4j组装Prompt交给LLM生成答案

> 
> 👉 适合：既要利用RAGFlow强大文档解析能力，又需要Java代码层自定义Agent逻辑。

# 📘 SpringBoot 调用 RAGFlow API 实操示例

> 
> RAGFlow 的对话接口兼容 OpenAI 协议，也有原生接口文档。
> 官方文档地址：[https://ragflow.io/docs/dev/api_reference](https://ragflow.io/docs/dev/api_reference)

## 1、前置准备

1. 部署好RAGFlow，创建**知识库（Dataset）**，上传文档；再创建**助手（Assistant）**，绑定这个知识库。
2. 在RAGFlow页面，拿到：`API Key` 和 `Assistant ID`。
3. SpringBoot项目引入 `RestTemplate` / `OkHttp` / `OpenFeign` 或者 `org.springframework.boot:spring-boot-starter-webflux`。

## 2、示例：SpringBoot 使用 RestTemplate 调用RAGFlow问答API

```
import org.springframework.http.*;
import org.springframework.web.client.RestTemplate;
import java.util.HashMap;
import java.util.Map;

public class RagFlowClient {

    private final String ragFlowBaseUrl = "[http://127.0.0.1:8000/v1](http://127.0.0.1:8000/v1)";
    private final String apiKey = "ragflow-xxxxxxx"; // 替换你的RAGFlow API Key
    private final String assistantId = "xxxxxxxx-xxxx-xxxx"; // 你的助手ID
    private final RestTemplate restTemplate = new RestTemplate();

    public String chat(String question) {
        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_JSON);
        headers.set("Authorization", "Bearer " + apiKey);

        Map<String, Object> body = new HashMap<>();
        body.put("assistant_id", assistantId);
        body.put("messages", new Object[]{
                Map.of("role", "user", "content", question)
        });
        // stream: false 非流式；true为流式返回
        body.put("stream", false);

        HttpEntity<Map<String, Object>> request = new HttpEntity<>(body, headers);
        ResponseEntity<String> resp = restTemplate.postForEntity(
                ragFlowBaseUrl + "/chat/completions",
                request,
                String.class
        );
        return resp.getBody();
    }
}
```

> 
> 调用返回JSON包含：回答内容、引用的文档片段（citations），你可以在SpringBoot里解析citations，做溯源展示。

## 3、文档上传API（业务系统上传文档到RAGFlow知识库）

如果你的业务系统需要**由用户上传文件，自动入库RAGFlow**，调用RAGFlow文档上传接口：

1. 先调用文件上传接口，上传文件，拿到`file_id`
2. 再调用文档添加接口，把`file_id`加入指定Dataset知识库。> 
> 文件解析、分片、向量化全部交给RAGFlow后台异步处理，SpringBoot只需要轮询文档状态接口判断是否解析完成。

# ⚖️ 企业场景选型建议

## ✅ 优先选【方案A】SpringBoot直接调用RAGFlow（大多数企业）

适用：

- 主业务是SpringBoot，**核心诉求是文档问答**（PDF/Word带表格，RAGFlow强项）
- 不想维护向量库、文档解析、分片、重排这些组件
- 后续RAG调参交给算法/产品人员在RAGFlow页面配置，不需要发Java服务版本

业务职责边界：

- SpringBoot：用户登录、权限、订单/业务数据、记录问答日志、前端接口封装、调用RAGFlow、结果二次过滤
- RAGFlow：RAG全链路，文档管理、向量存储、检索、LLM调用

## ✅ 选【方案B】LangChain4j + RAGFlow，适合下面场景：

- 需要复杂Agent逻辑：根据回答结果自动调用Java业务接口（Function Calling）
- 需要在Java代码里对检索回来的上下文做复杂过滤、业务数据拼接
- 多步骤任务编排：先查知识库，再查业务数据库，综合生成答案

## ❌ 不推荐：两套RAG并存（LangChain4j自建RAG + RAGFlow两套向量库）

维护成本翻倍，文档会存在两个地方，一致性很难保障。

# 📌 常见坑点

1. **网络隔离**：内网企业部署，SpringBoot服务要能访问RAGFlow的8000端口；RAGFlow还要能访问LLM服务（通义/DeepSeek等）
2. **鉴权**：RAGFlow的API Key不要放前端，**全部由SpringBoot后端转发请求**，防止泄露
3. **异步文档解析**：上传大文档不会立刻完成向量化，要做状态轮询，不要上传完马上提问
4. **流式输出**：前端打字机效果，SpringBoot可以用WebFlux转发RAGFlow SSE流

# 结论先说
**不是必须，但企业级生产环境强烈建议做一层网关（不一定非要 Spring Cloud Gateway），而且你规划的 DMZ 网关 + 内网AI服务这个架构思路是标准安全架构。**

> 关键点区分：
> LangChain4j 解决的是 **代码层模型/向量库抽象**（Java内部，切换模型不用大量改业务代码）；
> 网关（Gateway）解决的是 **服务访问层的流量、鉴权、限流、日志、安全隔离**（网络层面，和LangChain4j本身无关）。
>
> LangChain4j 是 SDK，在你的 AI 微服务（内网SF区）里面运行；网关是独立的流量入口，放在DMZ。

## 一、LangChain4j 的抽象 ≠ API网关的抽象
很多人容易混淆这两层，拆开看：
1. **LangChain4j（代码内抽象）**
    - 作用：在单个Java进程内部，统一 `ChatModel`、`EmbeddingModel`、向量存储接口；
    - 范围：JVM内部，**不对外暴露HTTP接口**；
    - 能力：切换 OpenAI / 通义 / Ollama / Milvus，只改配置，业务代码不变；
    - 局限：**没有任何流量管控、外部鉴权、限流、审计、网络隔离能力**。
    > 它管的是「代码怎么调用模型」，不管「外部系统怎么调用我的AI服务」。

2. **Spring Cloud Gateway / APISIX / Kong（API网关，DMZ层）**
    - 作用：所有客户端（前端、业务系统）统一入口；
    - 范围：HTTP流量入口，网络边界；
    - 能力：路由转发、统一token鉴权、QPS限流、调用量统计、黑白名单、请求日志、超时熔断、SSL、WAF；
    - 局限：**不理解LLM、RAG、Prompt，只转发HTTP请求，不处理AI业务逻辑**。

> 一句话：LangChain4j 解决**模型接入的多适配**；网关解决**AI服务对外暴露的统一管控**。两者互补，不是替代关系。

## 二、你设想的架构：DMZ网关 + 内网AI微服务（LangChain4j）
```
【外部/前端/业务系统】
        ↓（公网/办公网，只能访问DMZ）
【DMZ区：Spring Cloud Gateway】
    ✅ 统一鉴权、限流、计费/调用量统计、日志、WAF、熔断
    ✅ 路由：/api/ai/** → 转发到内网AI微服务
        ↓（内网SF区，DMZ到内网有限访问策略，不直接暴露AI服务）
【SF内网：AI微服务 SpringBoot + LangChain4j】
    ✅ LangChain4j：编排RAG、Agent、模型调用、向量库
    ✅ 内网才可以访问 LLM服务、向量库(Milvus等)
```
### 这个架构带来的收益（企业场景非常有价值）
1. **安全隔离（最核心）**
    AI微服务、LLM、向量库全部放在内网，**绝不直接暴露到DMZ/外网**。外网只能访问网关，网关做访问控制。即使AI服务有漏洞，攻击面被锁在内网。
2. **统一权限与调用计量**
    所有AI请求都经过网关：统一身份校验、按应用/用户统计调用次数、token消耗统计、限流防刷；不用每个LangChain4j微服务各自写一套鉴权。
3. **流量治理**
    AI场景很容易长耗时请求、流式SSE、大并发；网关统一做超时、重试、熔断、负载均衡。
4. **版本与路由灰度**
    多个AI微服务实例（不同RAG/Agent能力），网关做路由灰度发布，不改动调用方。

### 什么时候可以不用单独网关？
仅适合内部小范围使用：AI服务只给内网少数业务系统调用，没有外网访问，不需要统一鉴权、调用量统计。
> 只要这个AI能力要给多个业务系统、前端使用，或者有外网/办公网访问，**强烈建议网关**。

## 三、两种方案选型对比
### 方案1：独立网关（DMZ） + 内网LangChain4j AI微服务（推荐企业）
优点：
- 安全边界清晰，内外网隔离；
- 所有AI流量统一管控；
- AI微服务只关心AI业务逻辑（LangChain4j编排RAG/Agent），不用重复实现鉴权限流；
缺点：
- 多增加一个组件，运维复杂度上升；
- 流式SSE / WebSocket 需要网关支持转发（Spring Cloud Gateway可以支持）。

### 方案2：不做独立网关，LangChain4j微服务直接对外暴露
优点：架构简单，组件少；
缺点：
- 内网AI服务直接暴露，安全风险高；
- 每个AI服务都要独立实现鉴权、限流、日志；
- 调用量统计分散，很难全局管理；
> ❌ 企业生产，尤其有数据安全要求、敏感文档知识库场景，不推荐。

## 四、额外一个可选思路：网关层能不能再做一层模型统一抽象？
> 有两种抽象层次，不要混在一起：
1. **代码层抽象（LangChain4j）**：AI微服务内部，代码切换底层LLM供应商；
2. **网关层模型代理（可选增强）**：网关还可以做模型代理，类似 OpenAI compatible proxy，网关转发到不同LLM。
> 但模型代理**不替代LangChain4j**：模型代理只能转发LLM请求，**无法做RAG分片、检索、Agent工具调用、记忆管理**。RAG/Agent逻辑仍然要在内网AI微服务里由LangChain4j完成。

## 五、结合你前面RAGFlow的场景，扩展一下
如果你同时混合使用：`SpringBoot + LangChain4j + RAGFlow`
架构可以扩展为：
```
前端/业务系统 → DMZ网关 → 内网AI微服务(LangChain4j) → RAGFlow服务
```
- 网关：统一入口，鉴权限流；
- LangChain4j微服务：Agent编排、业务逻辑，调用RAGFlow API做知识库检索；
- RAGFlow：独立服务，文档解析、向量存储、RAG检索。

## 六、落地小提醒
1. AI场景大量用 **SSE流式输出**，选型网关时确认支持SSE；Spring Cloud Gateway支持SSE，但要注意连接超时配置；
2. Token用量统计：网关可以统计请求次数，但**token消耗需要AI微服务返回token信息上报网关/监控系统**；网关本身无法解析LLM的token；
3. 网关不要做太重业务逻辑：只做流量和安全，不要把RAG、Prompt编排放到网关；网关是流量转发，不是AI业务引擎。

# 架构说明

架构：**前端 → DMZ网关(Spring Cloud Gateway) → AI微服务(SpringBoot+LangChain4j，内网SF区) → RAGFlow(内网知识库服务) → LLM大模型服务**

> 
> 业务：用户提问，LangChain4j编排，调用RAGFlow做文档检索，拿到参考片段后组装Prompt，再调用LLM生成回答，结果原路返回前端。
> 包含：普通非流式问答时序；附带说明流式SSE版本差异。

# 一、组件清单

1. Client（前端/业务系统）
2. DMZ-Gateway：Spring Cloud Gateway（DMZ区，统一鉴权、限流、日志）

4. RAGFlow：独立RAG服务（文档解析、向量库、混合检索）
5. LLM Service：大模型服务（通义/DeepSeek/Ollama等）

# 四、关键要点说明（企业落地重点）

## 1. 职责边界

- **Gateway（DMZ）**：只管流量安全，**不参与任何RAG/LLM业务逻辑**；鉴权、限流、SSL、日志、熔断；SSE长连接转发，注意网关超时参数调大。
- **AI-Service（LangChain4j）**：编排层。对话记忆、query改写、调用RAGFlow检索、Prompt组装、LLM调用、结果校验、业务权限、Token消耗统计。**LangChain4j不负责文档入库、向量存储**，这块交给RAGFlow。
- **RAGFlow**：只负责文档管理+检索。只返回相关上下文片段，**不做最终答案生成**（和之前方案A的RAGFlow直接对话模式区分开）。> 
> 👉 本架构模式：**RAGFlow只做检索器，LLM生成交给LangChain4j编排**，灵活性更强，Agent能力可以在LangChain4j扩展。

> 
> 补充对比另一种模式：AI-Service直接调用RAGFlow `/chat/completions`，RAGFlow内部完成检索+生成，LangChain4j只做上层业务。两种模式都可行，上面时序是**RAGFlow纯检索**模式。

## 2. 两种RAGFlow集成模式区分（避免混淆）

### 模式①（上图时序）：RAGFlow 作为检索引擎（推荐你要Agent场景）

- AI-Service(LangChain4j) → RAGFlow检索接口 → 获取上下文；LangChain4j组装Prompt，调用LLM；
- 优点：LangChain4j完整掌控Prompt、Agent、工具调用；可以混合业务数据库结果+知识库内容一起回答。
- 缺点：RAGFlow的内置对话、引用渲染能力需要自己在Java侧处理。

### 模式②：RAGFlow 完整RAG+生成（简单知识库场景）

- AI-Service(LangChain4j) → RAGFlow `/chat/completions` API；RAGFlow内部检索+Prompt组装+调用LLM，直接返回答案；
- 优点：代码最少，RAGFlow页面调参即可优化检索效果；
- 缺点：LangChain4j很难介入检索后、生成前的Prompt编排，Agent能力受限。

## 3. 运维&安全注意点

1. DMZ网关不能直接访问内网RAGFlow/LLM；**只能由网关转发请求到AI-Service，AI-Service在内网访问RAGFlow和LLM**；网络策略最小权限。
2. Token消耗统计：网关统计请求次数；**token输入输出数量由AI-Service接收LLM返回的usage字段上报监控平台**，网关无法解析LLM payload。
3. RAG文档上传流程（不属于上面问答时序）：文档上传可以走两套路径：
   - 路径A：业务系统上传文件 → Gateway → AI-Service → RAGFlow文档上传API（统一入口）
   - 路径B：管理员直接登录RAGFlow WebUI上传文档（后台维护）

# 核心结论

SF内网区内的**业务微服务**调用同在内网的 `AI-Service(LangChain4j)`：

> 
> ✅ **优先：内网业务微服务直接调用 AI-Service（HTTP/Feign），不需要新增一层内网网关**
> ⚠️ **仅当内网有统一治理诉求时，才在内网SF区部署第二层网关（内网API网关，和DMZ网关是两套独立网关）**

先理清两个网关的定位，不要混淆：

1. **DMZ网关（Spring Cloud Gateway）**：面向**外部/办公网前端**，边界网关，解决外网进内网的安全隔离、防攻击。**不用于SF内网微服务之间调用**。
2. **SF内网网关（可选）**：只给内网各个微服务之间调用，用于统一治理，不是安全边界网关。

## 架构分区简图

```
【外网/前端】
     ↓ DMZ边界网关（DMZ区）
【SF内网】
├─ 业务微服务A、业务微服务B（SpringBoot业务系统）
├─ AI-Service（SpringBoot + LangChain4j）
├─ RAGFlow
└─ LLM服务
```

## 方案一：SF业务微服务 → 直接调用 AI-Service（推荐绝大多数企业）

调用方式：Spring Cloud OpenFeign / RestTemplate / WebClient。

### 适用场景

- SF内网可信域：业务微服务和AI服务都在内网，网络可信；
- 调用方都是内部微服务，数量不多；
- 内网已经有服务注册发现（Nacos/Eureka），可以直接服务名调用，不用写硬IP。

### 优点

1. **架构简单，少一层转发，延迟更低**；内网调用本身延迟很小，多一层网关会增加RTT、增加故障点。
2. 运维成本低，不需要维护第二套网关。
3. 服务发现天然支持：AI-Service注册到注册中心，业务微服务通过服务发现直接寻址。

### 要做的管控（**不需要网关也能实现**）

内网之间调用，鉴权、限流、调用量统计不用网关，在AI-Service自身实现：

1. **服务间鉴权**：内网微服务调用AI服务，用AppKey+Secret或者JWT，放在请求头；AI-Service接口拦截器校验。
2. **限流**：AI-Service内部做接口限流（Sentinel/Resilience4j），按调用应用维度限制QPS，防止某个业务微服务打爆AI服务。
3. **日志 & 埋点**：AI-Service接收请求时，记录调用方应用名、耗时、token消耗，上报监控系统(Prometheus)。
4. **熔断降级**：业务微服务侧用Sentinel/Resilience4j，AI服务不可用时熔断，避免级联故障。

> 
> 一句话：内网可信域，**限流、鉴权、熔断、监控，都可以在应用层实现，不需要网关**。

### 缺点

管控逻辑散落在AI服务本身；如果后续有几十上百个微服务调用AI服务，管理成本上升。

## 方案二：SF内网增加一套【内网API网关】（可选，适合大型企业中台）

架构：`SF业务微服务 → SF内网网关 → AI-Service`

> 
> 注意：这个网关**和DMZ的网关是两套独立组件**，职责完全不同，它不是外网边界，是**内网服务治理网关**。

### 什么时候才考虑上内网网关？

满足下面多条再考虑：

1. SF内大量微服务（几十个）都会接入AI能力；不止1~2个业务微服务调用AI-Service；
2. 企业要求**全内网所有服务API统一管控**：统一应用注册、统一密钥管理、统一全链路审计、统一路由、统一灰度发布；
3. 多套AI服务：未来不止一个AI-Service，会有多个AI微服务（不同Agent、不同知识库），内网网关做统一路由分发；
4. 安全规范强制：内网应用之间访问也必须走统一API入口，禁止服务直连（很多大型国企/金融会有这个规范）。

### 缺点

1. 多一层转发，增加链路延迟；
2. 多一个组件，增加运维复杂度，多一个故障点；
3. 内网网关**不替代DMZ网关**，两套网关要分别运维。

> 
> 常见选型：内网网关不一定用Spring Cloud Gateway，很多企业用 **APISIX、Kong** 做轻量内网网关，也可以复用现有中台网关（如果已经部署），不要单独新建一套。

## 两种调用路径完整总图（合并你前面DMZ架构）

```
【外部前端】
     ↓ DMZ网关（边界安全网关）
【SF内网】
    ├─ 路径1（外网来的请求）：DMZ网关 → AI-Service
    └─ 路径2（SF内网业务微服务调用）：
        ├─ 方案A（直连推荐）：业务微服务 → AI-Service（Feign+服务发现）
        └─ 方案B（中台治理）：业务微服务 → SF内网网关 → AI-Service
```

## 重要区分：两套流量来源，两套独立鉴权体系

1. **外网流量（前端）**：鉴权在DMZ网关，做用户/终端身份；
2. **SF内网微服务流量**：鉴权是**应用身份（AppKey）**，代表这个业务微服务应用，不是终端用户身份。> 
> AI-Service需要同时兼容两类请求入口，区分请求来源，做权限隔离。

## 推荐落地建议（你的场景）

你现在架构：SpringBoot业务微服务 + AI-Service(LangChain4j) + RAGFlow
👉 **起步阶段：SF业务微服务直接Feign调用AI-Service，不新增内网网关。**

- AI-Service内部：接入Sentinel做限流熔断；增加拦截器校验AppKey；埋点统计调用量、Token消耗；
- 监控：接入Prometheus，采集AI服务指标；
- 当后续接入AI服务的内网业务微服务越来越多，或者企业中台规范强制要求内网服务统一API管控，再引入内网网关。

# 核心方案：DMZ网关在转发请求时**主动增加自定义请求头标识**
> 不建议靠IP判断（IP维护麻烦、容易出错、云环境/容器环境IP会漂移）；**用网关注入的HTTP Header作为来源标记，是企业微服务标准做法**。

## 整体思路
1. **DMZ网关（Spring Cloud Gateway）**：在转发请求到内网AI-Service时，自动追加一个自定义Header，例如：
```
X-Request-Source: DMZ_GATEWAY
X-Request-App: WEB_FRONTEND
```
> 这个Header**只能由DMZ网关写入，内网请求禁止携带这个Header**；AI-Service收到请求，第一件事校验：如果是内网业务微服务发来的请求，但请求里带了`X-Request-Source: DMZ_GATEWAY`，直接拒绝（防伪造）。

2. **SF内网业务微服务调用AI-Service**：调用时**不携带 X-Request-Source**；而是携带应用身份Header：
```
X-App-Id: biz_order_service
X-App-Signature: xxxxxx（App签名/AppSecret）
```

3. AI-Service 收到请求后，根据Header分支处理两套权限逻辑：
- 如果存在可信的 `X-Request-Source: DMZ_GATEWAY` → **外网用户身份体系**（用户token，网关已经完成用户鉴权，AI服务校验用户权限）
- 如果不存在 `X-Request-Source` → **内网应用身份体系**（校验X-App-Id + App签名，代表SF业务微服务调用）

> ✅ 一句话区分：
> DMZ网关转发 → 网关注入来源标记；内网业务微服务直连AI-Service → 不带来源标记，携带应用密钥。

## 安全关键点（非常重要）
> ❌ 风险：内网调用方自己手动伪造 `X-Request-Source: DMZ_GATEWAY`，冒充前端请求。
> ✅ 防护手段：
> 1. AI-Service增加白名单IP段：**只有DMZ网关的后端IP，才允许请求携带 `X-Request-Source: DMZ_GATEWAY`**；
> 2. 内网SF网段发来的请求，如果携带该Header，直接拦截返回403；
> 3. 网关侧Header**不允许前端传入**，Spring Cloud Gateway配置覆盖，前端传的X-Request-Source会被网关强制覆盖/删除，防止前端伪造。

# 一、Spring Cloud Gateway（DMZ）配置示例（注入Header）
application.yml 配置片段
```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: ai-service-route
          uri: lb://ai-service
          predicates:
            - Path=/api/ai/**
          filters:
            # 删除客户端原始传入的X-Request-Source，防止前端伪造
            - RemoveRequestHeader=X-Request-Source
            # 网关注入来源标识
            - AddRequestHeader=X-Request-Source,DMZ_GATEWAY
```
> 效果：无论前端有没有传这个Header，网关都会先删掉，再重新写入。前端无法伪造。

# 二、AI-Service 拦截器代码思路（SpringBoot）
写一个 `AuthSourceInterceptor`，实现 `HandlerInterceptor`，在Controller之前拦截。
逻辑伪代码：
```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    String source = request.getHeader("X-Request-Source");
    String clientIp = getClientIp(request);

    // 1. 如果携带DMZ来源标记
    if ("DMZ_GATEWAY".equals(source)) {
        // 校验：只有DMZ网关IP白名单才允许携带这个header
        if (!ipWhiteList.contains(clientIp)) {
            response.setStatus(HttpServletResponse.SC_FORBIDDEN);
            return false;
        }
        // ====== 外网用户权限逻辑 ======
        // 网关已经完成用户鉴权，把用户token放另外header，AI服务校验用户权限、知识库权限
        String userToken = request.getHeader("X-User-Token");
        if (!userTokenAuthService.checkUserToken(userToken)) {
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            return false;
        }
        // 存入上下文：标记本次请求来源为WEB用户
        RequestContextHolder.getContext().setRequestSource(RequestSource.DMZ_WEB);
    } else {
        // ====== SF内网业务微服务调用（无DMZ标记）======
        String appId = request.getHeader("X-App-Id");
        String appSign = request.getHeader("X-App-Signature");
        if (!appAuthService.verifyAppSign(appId, appSign)) {
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            return false;
        }
        // 存入上下文：标记本次请求来源为内网应用
        RequestContextHolder.getContext().setRequestSource(RequestSource.SF_INNER_APP);
    }
    return true;
}
```

## RequestContext 上下文对象（后续业务代码可以直接读取来源）
```java
public enum RequestSource {
    DMZ_WEB,      // DMZ网关过来的前端用户请求
    SF_INNER_APP  // SF内网业务微服务调用
}
```
后续在AI-Service的业务代码里，可以根据来源做差异化：
- 限流策略不同：WEB用户按用户限流；内网应用按AppId限流；
- 日志埋点区分来源；
- 知识库权限：WEB用户只能访问授权给该用户的知识库；内网应用可以访问应用绑定的知识库。

# 三、两套调用请求的Header对比
### 场景1：前端 → DMZ网关 → AI-Service
| Header | 值 | 说明 |
|---|---|---|
| X-Request-Source | DMZ_GATEWAY | 网关自动注入，前端不可伪造 |
| X-User-Token | 用户身份token | DMZ网关校验完用户后透传 |

### 场景2：SF内网业务微服务 → AI-Service（Feign调用）
| Header | 值 | 说明 |
|---|---|---|
| X-App-Id | biz_order_service | 调用方应用ID |
| X-App-Signature | xxxxxx | App签名，由AppSecret生成 |
> ❗**不携带 X-Request-Source**

# 四、备选方案（如果你不想用IP白名单）
> IP白名单在容器/K8s环境维护会有点麻烦，可以再加一层网关签名：
DMZ网关转发时额外增加一个 `X-Gateway-Signature`，用网关私钥签名；AI-Service用网关公钥验签。
- 优点：不依赖IP；
- 缺点：实现复杂度高一点，适合安全要求极高场景。

# 六、落地小坑提醒
1. **Feign调用内网AI服务时，不要自动带上DMZ的Header**；内网微服务Feign客户端不要配置全局X-Request-Source；
2. 日志：每次请求打印`RequestSource`来源，方便问题排查；
3. 限流隔离：两套来源**独立限流桶**，内网业务调用QPS配额和WEB用户分开，防止内网大流量把前端AI服务打挂；
4. 知识库权限隔离：WEB用户权限是**人维度**；内网应用权限是**应用维度**，权限模型分开。
