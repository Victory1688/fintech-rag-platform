# 数据模型与接口契约

> 关联文档：01-架构与技术落地方案、02-PRD、**04-工程骨架与实施路线、05-AI可观测与运维监控方案**
> 数据库：MySQL 8.0 / utf8mb4_general_ci / InnoDB
> 约定：主键统一 `bigint unsigned` 雪花 ID；时间统一 `datetime(3)`；逻辑删除用 `deleted tinyint default 0`；每个业务库表均预留 `tenant_id bigint default 0`（单租户恒为 0，为未来多租户留退路）

**v1.1 变更（可观测相关）**

| 变更 | 位置 | 原因 |
|---|---|---|
| 新增 `t_llm_eval_score` | §6.6 | LangFuse 的评分会随 Trace TTL 被清理，金融合规要求评估结论长期留档 |
| `trace_id` 规范统一为 **varchar(32) 小写 hex** 并加索引 | §5.1、§6.2 | 全链路改用 W3C Trace Context；不是 32 位 hex 就无法与 OTel / LangFuse 关联 |
| 新增 `traceparent` 请求头 | §8.1 | W3C 标准透传头；`X-Trace-Id` 退化为兼容用 |
| 枚举新增 `RagOutcome` / `ContentLevel` | §7 | 质量看板与采集档位的取值字典 |

**v1.2 变更（落库与回放落地）**

| 变更 | 位置 | 原因 |
|---|---|---|
| **接口路径统一补 `/api` 前缀** | §9.2~§9.6 | 此前文档写 `/chat/xxx`、`/retrieval/xxx`，代码实际暴露 `/api/ai/xxx`、`/api/retrieval/xxx`。网关**不做 RewritePath**、内外网共用同一路径契约，文档写错会让联调方按错路径调用 |
| 新增 `GET /api/ai/replay/{traceId}` | §9.2 | 「按 traceId 一键回放一次回答」的入口 |
| 新增 `POST /api/ai/eval/manual` | §9.2 | 人工评分是黄金集的唯一来源，也是校准自动评估器的基准 |
| 新增 `GET /api/retrieval/logs/trace/{traceId}` | §9.3 | 回放需跨服务取检索段（检索日志在 `rag_retrieval` 库） |
| 明确 `t_retrieval_log.result` 口径 | §5.1 | 原来只标注 `tinyint`，导致「空召回」与「检索失败」在库里无法区分 |
| 补 `t_llm_eval_score` 写入链路 | §6.6 | 表已就绪但无写入方；补齐三个来源与唯一写入口 |
| `RetrievalClient` 新增 `findLogsByTrace` | §10 | 回放的跨服务契约 |

**v1.2 已落地的表与写入方一一对应**

| 表 | 写入方（代码） | 触发时机 |
|---|---|---|
| `t_conversation` / `t_message` | `ChatPersistenceService` | 每次问答（首问自动建会话，用户与助手消息成对落库） |
| `t_message_citation` | `ChatPersistenceService.saveCitations` | 非空召回且回答成功时 |
| `t_token_usage` | `ChatPersistenceService.saveTokenUsage` | 每次模型调用后（取 LangChain4j 返回的**真实**用量） |
| `t_feedback` | `FeedbackController` | 用户点赞/点踩 |
| `t_llm_eval_score` | `LlmEvalScoreAppService`（**唯一写入口**） | 在线抽样 / 离线批次 / 人工评分三条来源 |
| `t_retrieval_log` | `RetrievalAppService.writeLog` | **全部四条出口**：成功（含空召回）、无授权阻断、异常、abort |

## 1. 分库设计

| 库 | 归属服务 | 表 | 说明 |
|---|---|---|---|
| `rag_platform` | rag-platform-service | 8 张 | 身份、凭证、配额、模型配置、脱敏规则、审计 |
| `rag_knowledge` | rag-knowledge-service | 5 张 | 知识库、ACL、Dataset 映射、文档、版本 |
| `rag_ingest` | rag-ingest-service | 3 张 | 入库任务、任务日志、本地消息表 |
| `rag_retrieval` | rag-retrieval-service | 3 张 | 检索日志、评测集、评测结果 |
| `rag_chat` | rag-chat-service | 6 张 | 会话、消息、引用、反馈、Token 计量、LLM 评估留档 |

**铁律**

1. 单库单写：一个库只有归属服务可写，其它服务只读（且推荐走 API 而非直连）。
2. 禁止跨库 JOIN。
3. 所有表必须带 `create_time` / `update_time` / `create_by`，审计需要。

### 2.3 t_app_credential（内网应用凭证）

```sql
CREATE TABLE t_app_credential (
  id             bigint unsigned NOT NULL,
  tenant_id      bigint       NOT NULL DEFAULT 0,
  app_id         varchar(64)  NOT NULL COMMENT '应用ID 如 biz_credit_apply',
  app_name       varchar(128) NOT NULL COMMENT '应用名称',
  app_secret_enc varchar(512) NOT NULL COMMENT 'AppSecret（AES 加密存储）',
  owner          varchar(64)  DEFAULT NULL COMMENT '责任人',
  qps_limit      int          NOT NULL DEFAULT 20 COMMENT 'QPS 上限',
  daily_limit    bigint       NOT NULL DEFAULT 100000 COMMENT '日调用量上限',
  ip_whitelist   varchar(512) DEFAULT NULL COMMENT '调用方 IP 白名单，逗号分隔，空=不限',
  status         tinyint      NOT NULL DEFAULT 1 COMMENT '1启用 0禁用',
  expire_at      datetime(3)  DEFAULT NULL COMMENT '过期时间，空=长期',
  create_time    datetime(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  update_time    datetime(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  create_by      varchar(64)  DEFAULT NULL,
  deleted        tinyint      NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_app_id (app_id, deleted)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='内网应用凭证';
```

> **密钥轮换**：同一 `app_id` 允许存在多条记录（不同 `app_secret_enc`），两条同时启用即为轮换期；旧记录设 `expire_at` 到期自动失效。因此 `uk_app_id` 需改为 `(app_id, deleted, expire_at)` 唯一——落地时按此调整。

  event_type    varchar(32)  NOT NULL COMMENT 'QUERY / RETRIEVAL / INGEST / KB_CHANGE / AUTH / CONFIG_CHANGE',
  request_source varchar(16) NOT NULL COMMENT 'DMZ_WEB / SF_INNER_APP',

  client_ip     varchar(64)  DEFAULT NULL,
  resource      varchar(128) DEFAULT NULL COMMENT '资源，如 /api/ai/chat',
  kb_ids        varchar(512) DEFAULT NULL COMMENT '涉及知识库ID列表',
  doc_ids       varchar(2048) DEFAULT NULL COMMENT '涉及文档ID列表',
  detail        json         DEFAULT NULL COMMENT '明细（脱敏后的请求/响应摘要）',
  result        tinyint      NOT NULL DEFAULT 1 COMMENT '1成功 0失败',
  error_code    varchar(64)  DEFAULT NULL,
  cost_ms       int          DEFAULT NULL,
  event_time    datetime(3)  NOT NULL,
  create_time   datetime(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_subject_time (subject_type, subject_id, event_time),
  KEY idx_event_time (event_type, event_time),
  KEY idx_trace (trace_id)

```

> **留存与性能**：审计表是写入最重的表。建议按月分区（`PARTITION BY RANGE (TO_DAYS(event_time))`），并配置冷归档任务；查询侧只允许按 `subject + 时间范围` 或 `event_time` 走索引。

**`result` 字段口径（v1.2 明确，务必按此实现）**

| 值 | 含义 | 对应场景 |
|---|---|---|
| `1` | 检索流程**正常完成** | 含「召回成功」与「空召回」两种情况 |
| `0` | 检索**失败** | RAGFlow 调用失败、超时、依赖不可用等 |

区分这两者是必需的：`result=1 且 chunk_count=0` 才是「知识缺口」，
`result=0` 是「系统故障」—— 二者在运营端的整改动作完全不同（前者补文档、后者修系统）。
若一律记成 1，故障期的流量缺口会被误读成「知识库覆盖度突然变好」。

**三条落库纪律**

1. **所有出口路径都要写日志**：成功/空召回、无授权知识库、授权与意图无交集、检索异常。
   早期实现漏掉了后三条 —— 而那恰恰是「越权尝试」与「检索报错」的唯一线索；
2. **`trace_id` 取服务端链路值**（`RequestContext.currentTraceId()`），
   不得使用请求体里客户端传来的 `traceId`：审计字段采用客户端值等于「填什么记什么」，
   一旦填错，这条检索记录就与真实链路永久失联；
3. **`cache_hit` / `rerank_used` 写真实值**，不得硬编码 ——
   曾经这里把 `cache_hit` 写死 0，于是「缓存命中率」看板永远是一条压平的直线，
   而没人会怀疑数据源本身。

  reason         varchar(1024) DEFAULT NULL COMMENT '评分理由；**禁止写入问答原文**，只写结论与依据类型',

  create_by      varchar(64)  DEFAULT NULL,
  PRIMARY KEY (id),
  KEY idx_trace (trace_id),
  KEY idx_message (message_id),
  KEY idx_batch (eval_batch_no, metric_code),
  KEY idx_metric_time (metric_code, create_time),
  KEY idx_source (eval_source, create_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='LLM 回答质量评估留档';
```

**为什么必须落本地库（而不是只看 LangFuse）**

| 原因 | 说明 |
|---|---|
| TTL 冲突 | LangFuse 的评分随 Trace TTL 被清理，而合规要求「答案质量评估结论」长期留档（≥ 6 个月） |
| 最小化落盘 | 本地只留**分数与结论**，不留问答原文；即使安全评审不接受 ClickHouse 出现文本，质量报告照样能出 |
| 可回归 | 离线评测批次按 `eval_batch_no` 聚合，可直接作为发版门禁的判据来源（见文档 05 §8.3） |
| 可对齐 | `trace_id` 同时存在于 `t_message`、`t_retrieval_log`、`t_llm_eval_score`，三方按同一 traceId 关联，无需额外映射表 |

> **写入纪律**：`reason` 字段严禁写问答原文或召回片段全文；`judge_model` 与 `prompt_version` 必须写快照值，否则历史分数无法归因到具体的 Prompt 改版。

**写入链路（v1.2 落地）**

三个来源，一个写入口：**所有写入必须经 `LlmEvalScoreAppService.record(...)`**，
禁止任何地方直接 `insert` —— 因为四条纪律（指标白名单 / 量纲 / reason 防污染 / passed 服务端计算）
都在那里，绕过去就等于放弃了它们。

| 来源 | 触发者 | 当前状态 | 说明 |
|---|---|---|---|
| `ONLINE` | `OnlineEvalSampler` | **已落地** | 回答交付后异步抽样，**不阻塞用户**；有界队列，队列满即丢样本（丢样本无害，拖慢回答有害） |
| `BATCH` | 离线评测任务 | 契约就绪，实现待补 | 发版门禁的**唯一合法来源**（样本固定、可复现）；用 `eval_batch_no` 聚合 |
| `MANUAL` | `POST /api/ai/eval/manual` | **已落地** | 仅限内网调用；不接收 `passed` / `judge_model`，防止刷分 |

**在线抽样当前只计算「无需裁判模型」的指标**：`CITATION_COVERAGE`、`CONTEXT_PRECISION`。
`FAITHFULNESS`、`ANSWER_RELEVANCY`、`HALLUCINATION` 需要 LLM-as-judge，接入前**刻意不计算**。

> 这一点值得强调：用规则硬凑一个「忠实度 0.87」比不写更危险 ——
> 它会让团队误以为幻觉已在监控之中，从而错过真正的防线建设。
> 代理指标的 `judge_model` 统一写 `rule-proxy`，不写真实模型名，
> 以免后续按 `judge_model` 归因时把「规则算的分」当成「模型评的分」。

| 枚举 | 取值 | 说明 |

| `RequestSource` | `DMZ_WEB` / `SF_INNER_APP` | 请求来源，由网关注入标识决定 |

| `AnswerType` | `ANSWERED` / `NO_HIT` / `GUARDRAIL_BLOCKED` / `ERROR` | 答案类型（落库 `t_message.answer_type`） |
| `RagOutcome` | `ANSWERED` / `NO_HIT` / `GUARDRAIL_BLOCKED` / `ERROR` | **可观测侧的结果归因**，取值与 `AnswerType` 严格同词汇，作为 `rag_chat_answer_total{outcome}` 与 Collector 尾部采样的匹配依据。**禁止引入同义异名**（历史上曾用 `ABSTAINED`，已统一为 `NO_HIT`） |
| `ContentLevel` | `METRICS_ONLY`(默认) / `FINGERPRINT` / `REDACTED_CONTENT` / `FULL_CONTENT` | 可观测内容采集档位。配置项 `rag.observability.content-level` 取**枚举名**；`FULL_CONTENT` 受 `allow-plain-text-content` 防呆闸约束 |
| `EvalSource` | `ONLINE` / `BATCH` / `MANUAL` | 评估来源（`t_llm_eval_score.eval_source`） |
| `ParseStatus` | `PENDING` / `UPLOADED` / `PARSING` / `PARSED` / `FAILED` / `OFFLINE` / `CANCELED` | 文档解析状态机 |
| `KbCategory` | `PRODUCT` / `POLICY` / `REGULATION` / `INTERNAL` / `CASE` | 知识库分类 |
| `AuditEventType` | `QUERY` / `RETRIEVAL` / `INGEST` / `KB_CHANGE` / `AUTH` / `CONFIG_CHANGE` | 审计事件类型 |
| `GranteeType` | `USER` / `ROLE` / `DEPT` / `APP` | ACL 授权对象类型 |
| `GuardrailType` | `NO_HIT` / `MISSING_CITATION` / `SENSITIVE` / `CROSS_KB` / `UNSUPPORTED_NUMERIC` | 护栏命中类型 |

**状态机合法迁移**

```
PENDING  → UPLOADED | CANCELED
UPLOADED → PARSING  | FAILED | CANCELED
PARSING  → PARSED   | FAILED
FAILED   → UPLOADED（重试，retry_count < max_retry）
PARSED   → OFFLINE
OFFLINE  → UPLOADED（重新上线）
```
> 状态迁移必须经统一的状态机校验，禁止在业务代码里散落 `if (status == X) update(Y)`。

## 8. 请求头与统一返回约定

### 8.1 请求头

| Header | 方向 | 必填 | 说明 |
|---|---|---|---|
| `X-Request-Source` | 网关注入 | 外网流量必带 | `DMZ_GATEWAY`。内网流量**禁止携带**，携带即 403 |
| `X-User-Token` | 网关透传 | 外网流量必带 | 用户 JWT |
| `X-User-Id` | 网关透传 | 外网流量必带 | 网关校验后解析出的用户 ID |
| `X-App-Id` | 内网调用方 | 内网流量必带 | 应用 ID |
| `X-App-Timestamp` | 内网调用方 | 必带 | 毫秒时间戳，与服务端偏差 > 5 分钟拒绝 |
| `X-App-Nonce` | 内网调用方 | 必带 | 随机串，配合 Redis 做防重放 |
| `X-App-Signature` | 内网调用方 | 必带 | HMAC-SHA256(method + path + timestamp + nonce + sha256(body), appSecret) |
| `traceparent` | 网关生成 / 全链路透传 | 链路入口必带 | **W3C Trace Context 标准头**，格式 `00-{32位小写hex}-{16位小写hex}-{2位hex}`。**客户端传入值一律被网关丢弃**（防伪造链路污染）；服务间经 `feign-micrometer` 自动透传 |
| `X-Trace-Id` | 全链路 | 可选 | 业务自定义追踪头，**仅作兼容与人工排障**用；取值必须是合法的 32 位小写 hex。新代码统一用 `traceparent` |
| `X-Gateway-Signature` | 网关（可选强校验） | 否 | 网关私钥签名，AI 服务公钥验签 |

**追踪头三条硬约束**

1. `traceId` 必须是 **32 位小写十六进制**（`[0-9a-f]{32}`）。一旦自造格式（加前缀、混入大写或非 hex 字符），OTel / Collector / LangFuse 无法把它当作父上下文，会另起一条新链路 —— 现象是「日志里有 traceId，但链路里查不到」。
2. **`span-id` 不得全零**：W3C 规范明确「全零 span-id」的 `traceparent` 属非法值，会被下游直接丢弃。网关生成透传头时若没有真实 spanId，必须替换为合规随机值（`TraceIds.formatTraceparent` 已内置处理）。
3. **网关是链路的唯一根**：客户端传入的 `traceparent` 必须被网关**先删后写**。洗白动作放在 WebFilter 层（order 恰为 `Ordered.HIGHEST_PRECEDENCE`），必须早于 Spring Boot 观测过滤器的 `HIGHEST_PRECEDENCE + 1`；若放在 Gateway 的 GlobalFilter 里就太晚了 —— 那时伪造值已被采纳为本次链路的父上下文。

> **路径契约提醒**：本服务 Controller 直接映射 `/api/ai/**`，网关**不做 RewritePath**，
> 内外网共用同一路径。此前本节写作 `/chat/completions` 是笔误 —— 那会让联调方按错路径调用，
> 且与 `SourceAuthInterceptor` 的 `public-paths` / `gateway-only-paths` 配置失配。

**回放接口的准入（重要，不是可选项）**

回放会返回**他人的问答记录与引用信息**，属于内网运维能力，因此有三道约束：

1. 网关路由白名单**不得包含** `/api/ai/replay/**`；
2. 服务侧校验 `X-Request-Source != DMZ_WEB`（纵深防御，不赌网关配置永不出错）；
3. 每次调用都写审计（谁、何时、查了哪条 trace）—— 「查看别人的问答」本身就是敏感操作，
   必须留痕，否则「运维可以静默浏览任何用户的问答」会成为安全评审的一票否决项。

**内容可见性由内容档位统一裁决**

回放默认**不返回任何问答原文与片段原文**（`contentOmitted=true`），
即便传 `?withContent=true` 也仍受 `rag.observability.content-level` 最终约束：
`METRICS_ONLY` / `FINGERPRINT` 档位下正文不返回，并在响应的 `degraded` 里说明原因。

| `IngestClient` | rag-ingest-service | `upload(...)` | knowledge（可选） |

> **Feign 使用规范**
> 1. `rag-api` 中只定义接口与 DTO，**不写实现**；各服务通过 `@EnableFeignClients(clients = {...})` 显式引入。
> 2. 所有 Feign 调用必须配置**独立超时**：鉴权类 300ms、检索引擎类 3000ms、生成类 60000ms。
> 3. 所有 Feign 调用必须配 fallback：`platform` 不可用时，鉴权类走 **fail-close**（拒绝请求），非关键类走 fail-open（降级）。
> 4. `rag-api` 同时作为内网业务方的接入 SDK：业务方只需引 `rag-api` + 配置 AppKey 即可调用 `/internal/chat/completions`。
