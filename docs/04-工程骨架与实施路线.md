**分层约定（每个服务一致，禁止跨层）**

```
api/       对外接口层：Controller + Request/Response。只做参数解析与结果包装，不写业务
app/       应用层：用例编排。事务、状态机、跨服务调用都在这里
domain/    领域层：实体、枚举、状态机、仓储接口
infra/     基础设施层：persistence / client / mq / cache / storage / security
config/    Spring 配置
```

## 4. 版本风险提示（务必逐条确认）

| # | 风险 | 说明 | 处置 |
|---|---|---|---|
| V1 | **Spring Boot / Cloud / Cloud Alibaba 必须成套** | 只升其中一个会导致 Nacos 装配失败 | 用官方对照表整组升级 |
| V2 | **Spring Cloud Gateway 配置前缀** | 4.2 起前缀搬迁为 `spring.cloud.gateway.server.webflux.*`，5.x 可能移除旧前缀 | 若路由不生效，整体替换前缀（yml 内已注释提示） |
| V3 | **LangChain4j 1.x API 变动较频繁** | `StreamingChatResponseHandler`、`ChatResponse` 等包路径与签名在不同小版本间调整过 | 骨架用 FQN 写出关键类型，锁定版本后按 IDE 提示微调 |
| V4 | **JJWT 0.12.x 与 0.11.x 不兼容** | `parserBuilder()` 已废弃 | 已按 0.12 写法（`Jwts.parser().verifyWith(...)`） |
| V5 | **MyBatis-Plus 3.x 扩展包结构变动** | `PaginationInnerInterceptor` 迁包 | 见待补齐项 P0 |
| V6 | **`@ConditionalOnBean` 在自动配置中的时序** | `RagServerAuthAutoConfiguration` 依赖 `PlatformClient` 是否已被注册 | 已设计为 fail-fast；若启动报缺 `AppVerifierPort`，改为在各服务显式声明该 Bean |
| V7 | **RAGFlow 官方镜像仅 x86** | ARM64 需自行构建 | 部署前确认硬件架构 |
| V8 | **版本号需实时核对** | 骨架中的版本号按 2026-09 主流组合给出 | 以 start.spring.io / mvnrepository 实时版本为准 |
| **V9** | **缺 `feign-micrometer` 会导致跨服务链路静默断裂** | Spring Cloud OpenFeign 在 Boot 3 下**不会**自动透传 `traceparent`；现象是「网关→第一个服务正常，服务之间另起一条新链路」，极难排查 | 所有声明 openfeign 的模块已显式引入该依赖；`TracePropagationInterceptor` 已加**启动期体检**（缺失即 ERROR + 修复片段）。**从 pom 里删掉它会立刻退化为盲飞** |
| **V10** | **OTel GenAI 语义约定全部处于 Development** | GenAI 文档已迁至独立仓库 `semantic-conventions-genai`，无 tag 发布，属性名仍可能变更（如 `gen_ai.system` → `gen_ai.provider.name`） | 属性/指标/span 名统一走 `GenAiSemconv` 常量层，改名只改一处；用 `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` 统一开关；锁定版本后对照 changelog 升级 |
| **V11** | **LangFuse v3 是 6 个有状态组件** | 比「一个 Prometheus」重得多（约 14 vCPU / 18 GB），且**对象存储是必需项** | 团队 < 5 人时先只做 Prometheus + Grafana + Alertmanager；接入只走 OTLP（旧 Ingestion API 2026-11-16 日落），保证 v4 迁移是配置级而非代码级 |
| **V12** | **`management.tracing.propagation.type` 若被改成 b3** | OTel Collector 与 LangFuse 都解析不了 `traceparent`，两条链路 traceId 全部对不上 | 6 个服务的 yml 已**显式**声明 `type: w3c`，不要删 |
| **V13** | **Prometheus 是 pull 模型** | 不存在「Collector 把指标 push 给 Prometheus」这种数据流；网关 public-paths 若放开 `/actuator/**` 等于对外暴露 env/heapdump | 采集器直连各服务 `/actuator/prometheus`；网关只放行 `/actuator/health` |

## 5. 本地联调：快速开始

### 5.1 依赖中间件（docker-compose 参考）

```yaml
# docker-compose-infra.yml —— 仅用于本地联调，生产请按 HA 方案部署
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root123
      MYSQL_DATABASE: rag_platform
    ports: ["3306:3306"]
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--requirepass", "redis123"]
    ports: ["6379:6379"]
  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: minioadmin
      MINIO_ROOT_PASSWORD: minioadmin
    ports: ["9000:9000", "9001:9001"]
  nacos:
    image: nacos/nacos-server:v2.4.3
    environment:
      MODE: standalone
      MYSQL_SERVICE_HOST: mysql
    ports: ["8848:8848", "9848:9848"]
```

建库（4 个逻辑库）：

```sql
CREATE DATABASE rag_platform  DEFAULT CHARSET utf8mb4;
```

### 5.4 构建与启动

```bash
# 全量构建
mvn -T 1C clean install -DskipTests

# 单个服务及其依赖
mvn -pl rag-chat-service -am clean package -DskipTests
java -jar rag-chat-service/target/rag-chat-service.jar
```

启动顺序：

```
0) 可观测底座（可选，但建议先起 —— 服务一起来就有链路可看）
   cd deploy/observability && ./init-secrets.sh && docker compose -f docker-compose-observability.yml up -d
   （LangFuse v3 六件套 + OTel Collector + Prometheus + Grafana + Alertmanager，详见该目录 README）

1) MySQL / Redis / Nacos / MinIO / RAGFlow
   → rag-platform-service   （被所有服务依赖，必须最先起）
   → rag-knowledge-service
   → rag-ingest-service
   → rag-retrieval-service
   → rag-chat-service
   → rag-gateway
```

> 为什么观测底座要放在最前面：链路一旦在服务启动后才补上，**启动期的初始化链路永远是断的**，
> 后续排查「服务为什么起不来」时缺少最需要的那一段。观测底座与业务**无强依赖**，
> 它挂了业务照常运行（降级矩阵见文档 05 §10.3），所以「先起」不增加启动风险。

## 6. 编码规范约束（建议写入团队规约）

| # | 规则 | 原因 |
|---|---|---|
| 1 | 所有对外接口返回 `R<T>`，禁止裸对象 | 错误码与 traceId 要统一 |
| 2 | 业务异常用 `BizException`，禁止 `throw new RuntimeException("...")` | 错误码可观测 |
| 3 | 事务只包本地库，禁止把 RAGFlow / LLM / MinIO 调用放进 `@Transactional` | 长事务会拖垮连接池 |
| 4 | 跨服务调用必须显式声明超时，鉴权类 ≤ 500ms | 防止级联雪崩 |
| 5 | `datasetIds` 只能来自服务端推导，禁止使用请求体传入值 | 越权防护 |
| 6 | 缓存 Key 必须用 `RetrievalCacheKeyBuilder`，禁止手写 | 少一个维度就是越权 |
| 7 | 外部系统调用一律有「状态 + 重试 + 人工兜底」，禁止裸重试 | 分布式一致性 |
| 8 | 密钥/JWT/AES Key 只走环境变量或配置中心加密项 | 合规 |
| 9 | 内网 Feign 客户端禁止添加 `X-Request-Source` | 会被判为伪造并 403 |
| 10 | 引入 `rag-api` 的业务方需设 `rag.server.auth.enabled=false`（默认已关） | 避免把服务端拦截器装到业务方自己的接口上 |
| **11** | **埋点名称 / 属性名 / 指标名只能引用 `GenAiSemconv` 常量，禁止在业务代码写死字符串** | GenAI 语义约定仍在 Development，改名时只改一处；写死则看板与代码必然漂移 |
| **12** | **指标标签只允许枚举型有界维度**，禁止 `traceId` / `userId` / `conversationId` / `query` | 无界标签会打爆 Prometheus 内存（`check_skeleton.py` 已自动拦截） |
| **13** | **声明 openfeign 的模块必须引入 `feign-micrometer`** | 缺它 Feign 调用不带 `traceparent`，跨服务链路静默断裂（启动期会打 ERROR） |
| **14** | **`traceparent` 只由网关注入，业务代码禁止手写或信任客户端传入值** | 手写会产生两个取值不同的追踪头；图省事信任客户端则链路可被污染 |
| **15** | **`rag.observability.content-level` 只能填枚举名**（`METRICS_ONLY` / `FINGERPRINT` / `REDACTED_CONTENT` / `FULL_CONTENT`） | 填 `L0`/`L1` 之类的简写会导致 Spring 绑定失败 |
| **16** | **SSE / 异步线程切换时必须传递上下文快照**（`RequestContext` + MDC + 父 span） | 线程池复用会丢 traceId，流式请求的链路恰好最需要追踪 |
